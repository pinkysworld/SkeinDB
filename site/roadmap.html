Phase 15 — Additional performance improvements

Done

T150 through T153 are now in place: interned-column schema flags persist separately from the catalog, single-table scan paths can precompile `eq`/`ne`/`in` predicates into ValueID comparisons, row/snapshot executors only materialize the columns the query still needs, eligible full scans now run through a 1024-row scan->filter->project batch loop, and the core MVCC layer exposes a validated visible-version cache keyed by row id plus snapshot bucket.

  • T152doneBatch (vectorized) scan/filter/project pipeline

Phase 16 — Storage durability & production readiness

Done

The storage engine went from zero durability guarantees to atomic fsync-durable writes, a row-level redo WAL with idempotent crash recovery (pinned by a torn-tail fault-injection test), deferred/batched snapshot flush, and query-time streaming for tables larger than RAM. Operationally: cooperative statement timeouts, a deeper Prometheus /metrics surface + slow-query log, a backup/restore CLI, non-fatal lock poisoning, opt-in WAL group commit, and an unauthenticated-exposure startup warning. A concurrent-write benchmark surfaced a major write-throughput bottleneck (per-mutation full-file fsyncs of the catalog/CDC/forensic logs); making the CDC + forensic logs append-only lifted single-writer inserts from ~22 to ~185/sec (~7x) with every crash-durability and tamper-evidence guarantee intact. Security: RBAC is now fully enforced on the RPC data path — per-role, per-token database scope, and per-user database grants. RBAC granularity is now role → database → table. High availability: automated fenced failover with a Raft-style leader-election vote round, quorum fencing, and a leadership epoch, so at most one primary ever accepts writes (opt-in) — running per shard as well as whole-cluster, and data-safe: the election prefers the most up-to-date replica (by replication progress) and a voter refuses any candidate less caught up than itself (Raft log matching), so failover cannot lose acknowledged writes. Replication is now self-healing: each write carries a primary-assigned log position, and a replica that falls behind (or joins late) automatically pulls the ops it missed from the primary's op-log buffer and catches up — no manual rebuild.

  • S1-4doneAtomic writes, WAL crash recovery, deferred flush, query-time streaming
  • OPSdoneStatement timeout, /metrics + slow-query log, backup/restore, panic-resilience, group commit
  • WPERFdoneWrite-path fsync reduction (append-only CDC/forensic logs, ~7x)
  • SECdoneRBAC on the RPC path — role + per-token database scope + per-user database grants
  • HAdoneAutomated fenced failover (whole-cluster + per-shard) — heartbeat detection, quorum fencing, leadership epoch, Raft-style vote round with log matching (data-safe election)
  • REPLdoneSelf-healing replication — op-log (term, seq), idempotent/gap-aware apply, leader-driven catch-up (a lagging replica pulls what it missed)
  • CONSdoneConsensus core — commit index (majority-ack) + failover election on true (term, index) log positions, so the elected primary provably holds every committed write
